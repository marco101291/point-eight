# C4 diagrams — Context and Container

M6 (optional per the spec). Rendered as Mermaid flowcharts rather than the `C4Context`/
`C4Container` diagram types Mermaid also supports: those aren't reliably rendered by GitHub's
bundled Mermaid version, while plain `flowchart` has been supported forever — the priority here is
a diagram that actually shows up when you open this file, not textbook-perfect C4 notation.

Both diagrams reflect what's actually running today, not the eventual vision: there's no end-user
client yet (the mobile client is planned for after M6, per the project roadmap), so the only real
consumer of the System right now is Marco, through the admin panel and the API directly.

## Level 1 — System Context

Who point-eight talks to, with the whole thing as one box.

```mermaid
flowchart TB
    enduser(["👤 End user<br/>the person being matched —<br/>no client built yet"])
    admin(["👤 Marco<br/>operates and watches the System decide"])
    system[["point-eight<br/>Matchmaking simulation:<br/>an institutional orchestrator unilaterally<br/>assigns matches, scored by a Monte Carlo<br/>compatibility engine"]]

    enduser -. "registers, gets matched<br/>(planned — no client yet)" .-> system
    admin -- "views matches, simulations,<br/>and live decisions" --> system
```

## Level 2 — Containers

The deployable units and how they actually talk to each other — see `docker-compose.yml` for the
exact ports each one publishes.

```mermaid
flowchart TB
    admin_actor(["👤 Marco"])
    enduser_actor(["👤 End user<br/>(future client)"])

    subgraph pointeight["point-eight"]
        panel["Admin Panel<br/>Next.js<br/>Markov graph, spaghetti plot,<br/>compound graph, live feed"]
        elsistema["El Sistema<br/>Java 21 / Spring Boot<br/>Matchmaking orchestrator,<br/>REST API, domain events"]
        elmotor["El Motor<br/>Python / FastAPI<br/>Compatibility engine,<br/>Monte Carlo + Markov simulation"]
        rabbitmq{{"RabbitMQ<br/>score.requested / score.computed"}}
        dbsystem[("Postgres — System<br/>users, matches")]
        dbengine[("Postgres — Engine<br/>simulation runs, trajectories,<br/>transitions")]
    end

    admin_actor --> panel
    enduser_actor -. "planned" .-> elsistema

    panel -- "GET /api/users<br/>GET /api/matches<br/>GET /api/events" --> elsistema
    panel -- "GET /api/v1/markov-graph<br/>GET /api/v1/matches/{id}/trajectories" --> elmotor

    elsistema -- "publishes score.requested<br/>(fire-and-forget)" --> rabbitmq
    rabbitmq -- "score.requested" --> elmotor
    elmotor -- "publishes score.computed" --> rabbitmq
    rabbitmq -- "score.computed" --> elsistema

    elsistema -- "JPA / Hibernate" --> dbsystem
    elmotor -- "SQLAlchemy (async)" --> dbengine
```

### Reading the async edge

`El Sistema → RabbitMQ → El Motor → RabbitMQ → El Sistema` is one logical request (`DEC-016`), not
two independent flows: Java publishes a score request and returns `202 Accepted` immediately: the
actual score lands later, consumed off a separate response queue — there's no synchronous
request/response pair between the two services anymore.
